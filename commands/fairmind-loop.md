# fairmind-loop

Run a Fairmind **task or user story** in **loop mode**: define an objective, machine-verifiable stop condition up front, then let an *executed* gate drive implement→verify→iterate until the checks pass — instead of prompting every turn. Interactive mode is unchanged; this is the opt-in loop driver.

## Usage

```bash
/fairmind-loop                # loop on the active Fairmind task/story
/fairmind-loop US-142         # loop on a specific story/task ref
```

## What it does

This command is the driver. The **gate** is the `loop-check.sh` Stop hook, which runs `run_gate_checks.py` on every stop attempt — so once the loop is armed, iteration is automatic and the loop cannot end until the stop condition holds (and the journal hook is satisfied).

## Operational quickstart (gotchas — save the cold-start reading)

Front-loaded so you don't re-derive these from the source. Read before touching `.fairmind/` — but **after** the opening banner (the plugin's hook prints it), and **silently**: no play-by-play of reference/engine/hook reads ("let me check how the engine resolves state…", "let me confirm the flags of…"). The user-facing narrative speaks loop language (objective, check, admission, budget, arm, iterate), never engine internals; the first substantive thing the user reads after the banner is the contract summary.

- **State discovery needs `base_path`.** The Stop-hook gate runs `run_gate_checks.py --cwd <repo>` with **no `--state`**, so it finds `loop-state.json` only via `.fairmind/active-context.json`'s **`base_path`** field (or the `FAIRMIND_BASE` env). Bootstrap `active-context.json` **with** `base_path` (e.g. `".fairmind"`) pointing at the folder holding `loop-state.json`, or the gate silently **no-ops** (exit 0 = "no active loop") and the loop never enforces.
- **A prior run's `active-context.json` is stale — repoint it, don't inherit it.** In a repo already used for a loop, `active-context.json` still carries the previous task's `base_path`/`task_ref`. If you inherit them, the gate resolves the *old* loop's `loop-state.json` (worst case a terminal prior loop → the gate no-ops → the new loop never enforces) and every pre-repoint trace op is attributed wrongly: to the old loop's ledger when the marker still claims that loop and it is still running, and otherwise to one of the two routed directories — safe, but not *this* run's ledger either. What the two routed directories MEAN — not a closed list of the ways a loop can end, which is a set this sentence cannot enumerate: `.fairmind/degraded/` (rows stamped `degraded_from`) says the marker is stale or unreadable — a crash, a `kill`, a hand close, still claiming a loop that is over; `.fairmind/no-loop/` says the marker is honest and those ledgers simply belong to a loop this session is not — the engine's own `mode: "closed"`, whose rows also carry `after_loop: "<that loop's ref>"`, equally an `interactive` marker left sitting over a `loop-state.json`, and — since the identity tests landed — a `mode: "loop"` marker over a live loop-state that names a different task in its `target.ref` or a different session in its `owner_session`. `INTERNALS.md`'s **Interactive mode vs loop mode** section holds the full routing table and is the authority; read it there rather than trusting this paragraph's shorter version. ⚠️ **Routing is not a substitute for the repoint, and one residual proves it:** a trace path is built from the context's own `task_ref` and ignores `base_path`, so an inherited `interactive` marker with no `loop-state.json` at `base_path` still appends this run's ops to `.fairmind/trace/<the old ref>.jsonl` — the previous loop's own trace file (measured 2026-08-16, hook driven directly). The repoint is an **engine step**, not a manual chore: run `loop_open.py --repoint --task-ref <ref> [--base-path <path>]` as the run's **first mutation** in Phase 0 (before any other `.fairmind/` write). It atomically read-merge-writes `active-context.json`, setting `task_ref` (and `base_path` when given) while preserving every other field, and bootstraps the minimal shape if the file is absent. Still surface the stale-context warning to the user when `active-context.json` names a different `task_ref` — but the repoint itself is the engine step, not a hand-edit you can forget.
- **Admission is live-RED, and the engine records the proof — nobody pre-writes it.** `admit_check.py` re-runs the check *now* and requires it to actually fail on the current code — author the check and admit it **while the code is still red**, before the maker fixes anything. `source.red_first_proof` is **optional at spec time**: when the checker's descriptor omits it (the normal case — the check doesn't exist yet when it's specified), a live-RED result at admission is what admits it, and `admit_check.py` **writes** `red_first_proof` (the observed value + the current commit) into `loop-state.json` itself. Do not hand-author `red_first_proof` before admission; if it's missing, that is expected, not a defect.
- **`--dry-run` evaluates regardless of `status`.** It never persists (no `save_state` call), so there is nothing to protect by refusing it on a not-yet-armed loop — the arm-time smoke (step 8) runs the full gate on the loop while it is still `specified`, before `--arm` is ever called. This is the read-only verb only: a plain invocation (no `--dry-run`, the shape the Stop hook uses) still refuses on any `status != "running"`, a plain invocation with no `loop-state.json` remains a no-op. An inspection with `--dry-run` and no state file exits nonzero: bootstrap the intended loop or correct the selected `--state` path before using it as acceptance evidence.
- **`validate-fairmind-path.sh` scopes `.fairmind/` writes to `active-context.json`'s `base_path`** (plus the root `active-context.json` itself) — a `..` segment or any path outside that scope is refused. Run the Phase 0 repoint (`loop_open.py --repoint`, which sets `base_path`) **before any other `.fairmind/` write** this run; once it has run, Write/Edit to `${FAIRMIND_BASE}/…` passes normally.
- **Two enforcement points, on two different events.** `loop-check.sh` (the gate) fires on **Stop** — the main orchestrator's turn ends only if the gate passes. `check-journal.sh` (the journal) fires on **SubagentStop** — a sub-agent that mutated non-`.fairmind/` code cannot finish until it writes a journal. (PCF-1: the journal hook was on `Stop` and gated on `CLAUDE_AGENT_NAME`, a variable the harness never sets, so it enforced for nobody; `Stop` never fires for a sub-agent at all. It now reads the sub-agent's `agent_type` from the `SubagentStop` payload and enforces for **any** code-mutating sub-agent, not a role allowlist. The main orchestrator never triggers `SubagentStop`, so it is still never journal-gated.)

### Phase 0 — Contract & budget (Technical Lead, one human touchpoint)

**Opening.** The **banner** and, on a first run in this repo, the stacked-loop **map** are printed for you by the plugin's `UserPromptExpansion` hook the moment `/fairmind-loop` is invoked — you do **not** print them. (A banner run from the command body as a Bash *tool* call is collapsed by the client to "Ran 1 shell command" and never shown; the hook emits it as a rendered `systemMessage` instead.) Your first user-visible action is the dashboard:

1. Render the **transactional dashboard** and **include its output in your message so it renders as a table**:

   ```bash
   python3 "${CLAUDE_PLUGIN_ROOT}"/scripts/loop_dashboard.py --md
   ```

   It is a Markdown table — an active-loop header + one row per loop (status, checks, iter, tier, tool-calls by kind, duration, best-effort tokens) + totals. Relay it **verbatim**: the script generates the exact table, so it stays deterministic; do not hand-edit it. A fresh repo shows an empty dashboard — that is correct, not an error. (This is the **run** dashboard; the **trace** ledger of tool ops under `.fairmind/trace/…` is a different artifact, summarised only in the Exit report.)

Then do the machinery reading **silently** — no play-by-play of engine/hook reads; the next thing the user reads is the contract summary.

1. Engage **the Technical Lead** to resolve context and bootstrap `.fairmind/` (Phase 0 + Phase 0b). The loop runs on **any repo, zero-config**, and the run's **first mutation** is the repoint — it both bootstraps an absent `active-context.json` and rescues a stale one from a prior loop, atomically, so no op that follows (the gate resolving `loop-state.json`, `trace-op.sh` naming the trace file) can land on the previous loop's `base_path`/`task_ref`:

   ```bash
   python3 "${CLAUDE_PLUGIN_ROOT}"/scripts/loop_open.py --repoint --task-ref <task-or-story-ref> --base-path .fairmind
   ```

   This writes the minimal shape the runtime needs — **`base_path`** (how the Stop-hook gate finds `loop-state.json`, per the quickstart gotcha above) and **`task_ref`** (how `trace-op.sh` names the trace file it attributes each mutation through; a missing `task_ref` silently costs every agent its attribution) — while preserving every other field already present:

   ```json
   {"mode":"loop","fairmind":"none","project":"<repo-name>","base_path":".fairmind","task_ref":"<task-or-story-ref>","decisions_start_line":0}
   ```

   The repoint of a **new** task also records how many lines `.fairmind/insights/decisions.jsonl` already holds under `decisions_start_line` (`0` when it holds none): the terminal flush sends every decision from that line on as this loop's and every earlier one unattributed. Never hand-edit it; re-running the repoint for the same task keeps it, and never adds one. **With no `decisions_start_line` in the file** — a context written before the mark existed, resumed on the same task — the flush cannot tell this loop's decisions from older ones and sends **every** pending decision unattributed; the next new-task repoint records the mark.

   Run it **before any other `.fairmind/` write** this run. When `active-context.json` already exists with a different `task_ref` (a prior loop), also **warn the user** that the stale context is being repointed — the repoint is the engine step that makes it safe, not a hand-edit you can forget. The Technical Lead then asks the user **once** whether a Fairmind workspace exists, recording the answer in the `fairmind` field (`none` | `configured`) — never re-asking while it stands. If yes, it tells them to run **`/fairmind-connect`** — which checks the MCP entry and the key and binds this checkout to the ingested repository — rather than walking them through Studio by hand.

   - **If — and only if — this repo is connected, stage the task context yourself before
     dispatching.** The Technical Lead holds no Fairmind tool (its `tools:` line is a literal
     roster and cannot follow a per-checkout mount name), so anything the platform knows about
     `<task-or-story-ref>` has to be fetched by **you** and written to
     `${FAIRMIND_BASE}/inbox/` — `task.json`, `user-story.json` and `tests.json` from
     `Studio_get_task`, `Studio_get_user_story` and `Studio_list_tests_by_userstory`, plus an
     `inbox.md` saying what came back empty and what failed. That is the same staging
     `/fairmind-develop` Phase 1a does, narrowed to what a loop actually needs: a loop compiles
     ONE task into a contract, so there is no roadmap to find and no task ordering to derive.

     🔴 **Standalone is the default and needs none of this.** `fairmind: "none"`, or no ref that
     resolves on the platform, means no inbox — the contract comes from the user or from
     `/loop-import`, exactly as before, and the Technical Lead is told so. Never block a loop on
     a fetch: a failed or empty retrieval is staged as such in `inbox.md` and the run continues
     standalone.

   - **Keep `.fairmind/` out of the customer's diff without touching their `.gitignore`.** The workspace is untracked noise in `git status`, and the reflex is to add a line to `.gitignore` — which is *their* file, lands in the PR, and gets flagged as an unrelated change (measured 2026-08-24: the loop wrote `.fairmind/` into the repo's `.gitignore` mid-run and it shipped in the diff, where the cross-model review called it out). Use the local, never-committed exclude file instead, **at Phase 0, before arming** — a fresh write while `running` is a git-visible mutation and trips `blocked_scope`:
     ```bash
     grep -qxF '.fairmind/' .git/info/exclude 2>/dev/null || echo '.fairmind/' >> .git/info/exclude
     ```
     If the repo *already* gitignores `.fairmind/`, change nothing. Only propose a real `.gitignore` edit if the user asks for one.
   - **Optional isolated worktree.** The Technical Lead may offer to run the maker's edits in a dedicated git worktree instead of the user's own checkout — **opt-in**, and least-urgent while this plugin is self-hosting its own tasks. If offered and accepted, create it before the maker's first turn:
     ```bash
     python3 "${CLAUDE_PLUGIN_ROOT}"/scripts/loop_worktree.py --create --task-ref <ref> --state "${FAIRMIND_BASE}/loop-state.json"
     ```
     Maker edits then land on branch `loop/<ref>` inside that worktree — the user's checkout stays untouched — and the exit report points at the `loop/<ref>` branch diff instead of the working tree. It is idempotent (safe to re-run; reuses the same worktree). Tear it down once the loop closes:
     ```bash
     python3 "${CLAUDE_PLUGIN_ROOT}"/scripts/loop_worktree.py --cleanup --task-ref <ref>
     ```
     Once `worktree.{path,branch}` is recorded, the gate **follows** it: every check verdict and the `contract.scope` boundary are evaluated against the worktree, not the user's own checkout (see `fairmind-gate/references/loop-state.md`'s `worktree` section). If the recorded path stops resolving to a real, registered worktree of this repo (removed on disk, or `--cleanup` ran without clearing `state["worktree"]`), the gate fails the whole evaluation closed to `blocked_worktree` rather than silently falling back to the main tree — see the Exit section below.
2. **The design brief comes FIRST — before a single criterion is classified.** The Technical Lead writes `${FAIRMIND_BASE}/design/<ref>.md`: where each invariant lives and which existing precedent in *this* codebase puts it there, which error class a new refusal uses and why not the neighbouring one, what precedent the change copies and where the analogy stops, the non-happy inputs per invariant, and what is deliberately out of scope. **Sized to the task** — five lines is a complete brief when the questions genuinely have one answer each. It is a *plan*, never a retrospective report. Full section contract: `fairmind-gate/references/design-brief.md`.

   **Why this is a step and not a nicety.** A compiled contract is a list of checkable claims, not a design, and the criteria are what the checks — and therefore the implementation — are bounded by. Measured 2026-08-24: a card whose prose said *"the route accepts it and validates it"* compiled to a contract that pinned the invariant at the HTTP boundary and left the store accepting anything. Every check went green on the **first** evaluation, the loop spent 0 of 8 iterations, `coverage` read **1.0**, and the shipped diff let any non-HTTP caller write an invalid row into an **append-only** log. Nothing in that contract could have caught it, because the contract was what was wrong. The brief is where that question gets asked.

   **The criteria are then derived from the brief's decisions, not from the ticket's sentences** — and the decisions the ticket never stated are put to the user *as decisions*, alongside the gap report, before anything arms. `coverage: 1.0` says every criterion has a check; it cannot say the criteria describe the right design, so it is not on its own a coaching moment.

   The brief lives under `.fairmind/`, so it is structurally exempt from `blocked_scope` and never lands in the diff the customer reviews. It is also the completeness reviewer's input at the Exit gate.
3. The Technical Lead **classifies** each acceptance criterion / objective into a check type and **specifies** descriptors into `${FAIRMIND_BASE}/loop-state.json` (using the `fairmind-gate` skill). The Technical Lead never writes check code. It also **persists the classified criteria into `contract.criteria[]`** — one entry per acceptance criterion, `{ id, text, disposition, hard }`, where `disposition` names the check that covers it (`checked:<id>` / `evidence:<id>` / `quarantined:<id>` / `unverifiable`) and `hard` defaults to `true` (see `fairmind-gate/references/loop-state.md`). **This is mandatory for arming, never inferred**: `--arm` refuses a loop whose `contract.criteria` is absent, null, or empty, and refuses any HARD criterion not covered by a live, admitted check — so a Phase 0 that skips this step produces a loop the engine will not arm. Optionally, the Technical Lead may also declare `contract.scope.allowed_paths` (a glob list) — the run's allowed mutation footprint. When declared, every gate evaluation cross-checks the run's git-derived mutation set against it *before* any check verdict is considered; a mutated path outside scope is a **terminal hard stop** (`status: "blocked_scope"`), never an ordinary red and never counted against budget. No declaration → identical to today (no-op). **A declared scope must cover *every* path a mutation lands on while the loop is `running` — not only the makers' code.** Only `.fairmind/` is auto-exempt (the loop's own workspace, dropped structurally by `_is_loop_workspace_path`); `--arm` additionally exempts files *already dirty at arm time* (`contract.mutation_set.baseline.pre_dirty`, anchored to their arm-time content). Anything written **fresh** while `running` — a run/findings log under `docs/`, a scratch artifact, a generated file — is a git-visible mutation and trips `blocked_scope` unless its path is in `allowed_paths`. So when you (orchestrator) or a maker will write to a path outside the code surface during the run — e.g. appending to this repo's internal log while internal — add that path to `allowed_paths` at spec time (finding F2). **A pre-compiled contract may be consumed instead of hand-authoring this step.** When the task originates from an external ticket run through `/loop-import`'s `--emit` (`task-compilation` skill + `scripts/loop_import.py`), its output is already a `loop-state.json` with `checks[]` and `contract.criteria[]` populated — reuse it (and its `.fairmind/contracts/<ref>.json` copy) as the starting point for this step instead of classifying from scratch, still confirming admission and coverage before arming.
4. The Technical Lead detects capabilities → **hermeticity tier** (`srt` present → A, else B), and **captures baselines** for reduce/improve goals.
5. Check authoring is **delegated to the checker-side, RED-first** (the QA Engineer for functional/evidence, the Code Reviewer for metric/performance, `sonar_gate.py` for static) — **maker ≠ checker**. Each authoring dispatch is **stateless and self-contained**, following `fairmind-gate/references/authoring-brief.md`: full descriptor inline, the four admission gates as acceptance criteria, exact output format, no scope expansion, and the INPUT GAP rule (missing input → say so, don't guess).
6. Run **admission**: `python3 "${CLAUDE_PLUGIN_ROOT}"/scripts/admit_check.py --state "${FAIRMIND_BASE}/loop-state.json"`. Quarantined checks are surfaced, excluded from stop. **A non-zero exit blocks arming**: `admit_check.py` exits non-zero when every check it evaluated in this run ended up quarantined, or when it considered zero checks at all (an admission run that admits nothing is never a success) — do not proceed to Phase 0b step 9 on a non-zero exit; fix or re-author the offending check(s) and re-run admission first. A check skipped as already admitted for its unchanged descriptor (`admission=skipped`) was not evaluated and does not count either way: it cannot turn a run whose new checks all failed into a 0 exit. Exit 0 means at least one evaluated check was admitted — a partial quarantine, where arming may proceed with the quarantined check(s) surfaced to the human — or that every check was skipped, with nothing new to admit.
7. The Technical Lead **proposes a budget** sized to the task and **asks the user to confirm or adjust it**. Default shape:
   - `max_iterations ≈ 2 × (number of admitted checks)` — headroom for a red-then-fix cycle per check.
   - `max_consecutive_failures = 3` — a check that fails three evaluations running is a strategy problem, not a budget problem.
   - `timeout_min` sizes the whole **arm→close** wall clock, not a single gate evaluation. Since T19, `--arm` stamps `budget.spent.started_at` at arm time, so the timeout clock runs across every maker/checker turn between arming and the loop's terminal transition — not just the gate's own (sub-second) execution. Size it from a realistic estimate of wall-clock time per iteration (dispatch + implement + verify), e.g. `timeout_min ≈ typical wall-clock minutes per iteration × (max_iterations + K)`, rounded up with generous headroom. The old single-evaluation-wall-time formula would trip `blocked_timeout` at the very first evaluation of every loop once the clock starts at arm — size for the **arm→close** span, not the gate's own runtime.

   Do not arm the loop until the user confirms.
8. **Arm-time smoke run:** the loop is still `specified` at this point — Phase 0b's bootstrap status, never yet armed. Run the full gate once via `--dry-run` and require **zero ERROR/INCONCLUSIVE** results — a missing runner, an unreadable report, a non-deterministic signal must surface now, at arm time, not on iteration 1 of a live loop. `--dry-run` evaluates the gate regardless of `status` and never persists, so it runs cleanly on the `specified` loop with no hand-edit required:
   ```bash
   python3 "${CLAUDE_PLUGIN_ROOT}"/scripts/run_gate_checks.py --dry-run
   ```
   If any check is ERROR or INCONCLUSIVE, fix the environment/descriptor (or quarantine the check) and re-run the smoke before arming.
9. **Start gate:** optionally inspect coverage read-only first, then arm with the engine's own verb — never hand-edit `loop-state.json.status`:
   ```bash
   python3 "${CLAUDE_PLUGIN_ROOT}"/scripts/run_gate_checks.py --validate-contract   # read-only: is this contract armable?
   python3 "${CLAUDE_PLUGIN_ROOT}"/scripts/run_gate_checks.py --arm
   ```
   Arm only when the budget is confirmed **and** the arm-time smoke run is clean. `--arm` runs the contract validation **internally** (its third refusal gate, after already-`running` and no-admitted-check) and **refuses an invalid contract**: every HARD `contract.criteria[]` entry must be covered by a live, admitted check, or `--arm` exits non-zero, names each uncovered criterion on stderr, and leaves `loop-state.json` byte-untouched (status not flipped, `started_at` not stamped, no arm audit entry). `--validate-contract` is the read-only twin that reports the same coverage without side effects — the verb a human runs to ask "is this armable?".

   **`--arm` also refuses a loop with no design brief** (step 2), naming the path it looked for and leaving `loop-state.json` byte-untouched; `--validate-contract` reports it on both paths and exits non-zero. ⚠️ The predicate is deliberately weak and says so: it proves a brief EXISTS and carries prose outside its headings, so it refuses the absent and the empty template. It cannot tell a brief that answered *where does this invariant live* from one that filled the heading and moved on — a genuinely five-line brief and a stub look alike from there. The completeness reviewer at the Exit gate is what catches the hollow one.

   **Decline-to-arm branch.** If a task's hard criteria cannot be covered by a live, admitted check — the check does not exist, the check is quarantined, or the criterion is genuinely `unverifiable` — do **not** arm a weak gate. The engine refuses, and the recommendation (from the engine's own stderr, and here) is to run the task in **interactive** mode instead, or to downgrade a genuinely advisory criterion to `hard: false` (which the coverage report then names as an accepted hole). A loop whose stop condition cannot be gated is not a loop; arming it anyway is exactly the failure this validation exists to prevent. Arming never proceeds on the orchestrator's own judgement of coverage — the engine decides, on the persisted contract.

   On a successful arm, `--arm` flips `status` to `running`, stamps `budget.spent.started_at` from its own clock (so the measured window starts when the work starts, not at the first gate evaluation), and zeroes `confirmations` — the same verb re-arms a `blocked_*`/`passed_pending_human` loop after a human gate rejection, preserving its original `started_at`. It also makes **the session that runs `--arm` the loop's owner** (`owner_session`), read from `CLAUDE_CODE_SESSION_ID` — the host sets it in every Bash subprocess, equal to the `session_id` its Stop hook receives — so another session ending turns in the same checkout cannot claim the loop first; a re-arm from a new session takes it over. With no session id available (a plain terminal), `owner_session` is cleared and the next session's Stop claims it. The stderr line names the owner it recorded. A non-zero exit means arming was refused (already `running`, no admitted check, or an invalid contract) — read the stderr reason before retrying. Once armed, render the dashboard (`python3 "${CLAUDE_PLUGIN_ROOT}"/scripts/loop_dashboard.py --md`, included in your message as a table) so the user sees the loop go live with its active-loop header.

   **Arming also stamps the loop's consent classes**, resolved from the repo-root `.fairmind-insights.json` at that instant (the classes and their defaults are in `INTERNALS.md` → *Consent classes*). The stamp is **frozen at collection** — a config edited between arm and flush cannot retro-label data already collected — and on a **re-arm** it is **intersected** with the stamp already there, never replaced: `iterations[]` is append-only across the whole loop lifetime, so one close can carry work collected under several arm windows, and a class is claimable only if every window that contributed data granted it. A narrowing therefore applies retroactively (over-withholding is safe); a widening never applies backwards.

   ⚠️ **A re-arm also clears the previous round's lifecycle records** — `gate_green` and `post_ceremony` (see the Exit section) describe the round the re-arm abandoned, so carrying them forward would make the engine report a confident wrong answer about a tree nobody shipped. The recorded human verdicts are the exception: that list is append-only and survives every re-arm, because the rejection history is the point.

### Phase 1..N — Iterate (automatic via the gate)

- **Maker turn:** The Software Engineer reads `${FAIRMIND_BASE}/steering.md` first, if present (the human steering channel — see Notes below), then **the design brief** (`${FAIRMIND_BASE}/design/<ref>.md`) — *before* the failing check bodies, because the brief is what says what to build and the checks only say what is measured — then implements (composing `fairmind-tdd` with the conventions the repository already follows), reads any prior gate feedback, and journals per iteration under the **apply-or-rebut** rule: every non-green item is either **APPLIED** (the code changed — say what) or **REBUTTED** (why it is wrong — flagged to the checker, never by editing the descriptor).
  - 🔴 **The checks are the FLOOR, not the ceiling.** A behaviour the brief calls for and no check covers is still required; the missing check is raised to the checker through the same apply-or-rebut channel, never silently skipped. Measured 2026-08-24, the maker's own journal on a loop that shipped a 5.4/10 diff: *"Read the three RED test bodies … in full before writing any code"*, and on the one real design question in the task, *"a hard requirement in the brief … rather than a design choice with alternatives, so there was nothing to weigh here."* Reading the design out of the failing tests is how a loop implements the test instead of the problem — and the gate goes green either way. Scope creep is still refused: what is in neither the brief nor a check is out.
  - **Drive the maker to completion within the turn.** The gate fires on *every* orchestrator turn-end. If the maker is dispatched as a background/async `Agent` that keeps writing after the turn ends, the gate evaluates a **half-written tree** — charging budget and firing spurious STRATEGY TURNs on merely-incomplete work, or advancing the confirmation streak on a *false green* whose RED-making test has not landed yet. So either dispatch the maker **synchronously**, or **hold the orchestrator turn open** until the maker's artifacts are complete (block on it — e.g. `TaskOutput(block:true)` — before ending the turn) so the gate only ever judges a finished tree. The engine has a **settle-window safety net** (H8): an evaluation whose most recent work-product write landed within the last `FAIRMIND_GATE_SETTLE_S` seconds (default 45) is treated as *in-flight* and does not move budget, `consecutive_failures`, or the confirmation streak — but that is a backstop for a forgotten hold, not a substitute for driving the maker to completion.
  🔴 **And the backstop is SILENTLY ABSENT when this session's `task_ref` is not the loop's `target.ref`** — declared here because nothing surfaces it at runtime. The settle probe reads `.fairmind/trace/<this context's task_ref>.jsonl`, and since the identity routing landed, a context naming a different task than the live loop-state has its capture routed to `.fairmind/no-loop/` instead, leaving that file empty. Measured on a fixture with the maker writing inside the window: `in_flight` true on every evaluation before the routing, absent after, `consecutive_failures` and `budget.spent.iterations` both running 1 → 2 → 3 and the loop hitting the terminal **`blocked_failures` at the third evaluation** — where the same fixture with the two refs agreeing stays `running` at 0/0 through the fourth. So on a divergent ref the freeze does not fire, and holding the maker's turn open is the whole protection rather than a belt on top of a brace. **The same empty file also costs that session's ops in the loop's Agentic Insights payload (1 → 0 rows measured) and in the dashboard**, which is the more permanent loss of the two — a verdict is recoverable by re-arming, data is not. The fix is the repoint you already owe Phase 0: `loop_open.py --repoint --task-ref <ref>` makes active-context name the loop it is driving. `INTERNALS.md`'s **Interactive mode vs loop mode** section carries the full residual.
- **Gate turn:** on every stop, `loop-check.sh` runs the checks. Not green + budget left → the hook blocks the stop and feeds structured feedback (routed to the owner) as the next turn's input. All green for **K ≥ 3 consecutive** evaluations → `status: passed_pending_human`.
  - **Reaching K on an already-green, settled tree does not require K empty turns (finding F3).** The Stop hook ticks the streak once per turn-end, but a real evaluation *is* just `run_gate_checks.py` (no `--dry-run`) — the same invocation the hook makes. So when the maker has landed a green tree and it is **stable** (nothing left to write), you may run that command directly, back-to-back, to accumulate the confirmation streak to K in a single turn, instead of ending K near-empty turns to let the hook tick. Each such run is a genuine, state-mutating evaluation (it advances `confirmations`), and the H8 settle window still applies — an evaluation within `FAIRMIND_GATE_SETTLE_S` (default 45s) of the last work-product write is treated as *in-flight* and will **not** advance the streak — so drive it only once the tree has genuinely settled, never to paper over a maker that is still writing. ⚠️ On a divergent `task_ref` that guard does not fire at all (see the settle-window note in the bullet above), and here its absence is a **false-green** risk rather than a budget one: K back-to-back evaluations would accumulate the streak over a tree still being written. Repoint first, or confirm the tree is settled by hand. And mind the shell timeout when a check runs the full test suite: at tens of seconds per evaluation, K back-to-back runs in one Bash call can outlive the Bash tool's default timeout (currently 120s) and the kill lands mid-evaluation — completed evaluations keep their persisted confirmations (recoverable, just wasteful) — so either raise the Bash timeout for the K-drive or run the evaluations one per command.
- **Commitment boundaries (warn-and-route, never auto-quarantine):** the gate watches iteration history for two stall signals. A check at **2 consecutive failures** (one below the cap) raises a **STRATEGY TURN**, routed once to the *checker* — is the check wrong, or the approach? Two checks **strictly anti-correlated** over the last 3 evaluations raise a **CONTRACT CONFLICT**, routed to the *Technical Lead* to reconcile the two criteria. Both only warn and re-route; the human decides.
- You can inspect without mutating state at any time:
  ```bash
  python3 "${CLAUDE_PLUGIN_ROOT}"/scripts/run_gate_checks.py --dry-run
  ```

### Exit — final human gate

- 🔴 **Green × K does NOT close the loop — the completeness review does.** The gate holds at `running` with the streak frozen at K (no budget spent) and routes the turn to the reviewer. This is the loop's **second exit check**, the one `fairmind-gate` has always named alongside the binary oracle: the checks answer *does it work*, and they cannot answer *is this the right work*, because a contract compiled from a ticket is exactly the thing that can be wrong. Measured 2026-08-24: a loop went green on its **first** evaluation, spent 0 of 8 iterations, and shipped a diff that let any non-HTTP caller write an invalid row into an append-only log — with every check green and `coverage` at 1.0.

  Dispatch the **Code Reviewer** (any role that owns no check — the engine reads the makers off the contract, so `maker ≠ checker` holds without a hardcoded list). Its input is **the design brief, the diff, and the contract**, and its four questions are in `agents/code-reviewer.md`; the headline one is *does the diff implement every decision in the brief, at the layer the brief named*. Then record the verdict:

  ```bash
  python3 "${CLAUDE_PLUGIN_ROOT}"/scripts/run_gate_checks.py --record-completeness complete \
    --by code-reviewer --attestation "${FAIRMIND_BASE}/attest/<ref>-code-reviewer-<n>.json" \
    --summary "<what the review concluded>"
  ```

  The attestation is written by the `record-attestation.sh` **SubagentStop hook** when the reviewer sub-agent finishes — you do not author it; list `${FAIRMIND_BASE}/attest/` and pass the newest one. It is spent on exactly one verdict, and a verdict whose mutation signature no longer matches the tree is refused as stale, so post-review edits mean a fresh review. A `gaps` verdict does not unblock: fix what it named (the checks staying green through that is expected — they were never the signal that would catch it) and have the reviewer record again. ⚠️ **This raises the cost of skipping the review; it does not make it impossible** — the attestation is a file under `.fairmind/`. Do not describe it to the user as more than that.
- **Green confirmed AND the completeness verdict recorded → `passed_pending_human`.** Present the report: what passed, each check's hermeticity tier, iteration count, advisory/quarantined checks, and what the completeness review concluded. **No auto-merge/deploy** — a human approves, then the Fairmind task status is updated.
- **Adversarial pass on top, for a gate/engine change.** If this loop changed the gate's own safety logic, the completeness review is necessary but not sufficient — run an independent "try to break each fix" pass (revert-on-scratch to prove each check has teeth; drive the real engine on the failing combinations) **before** presenting to the human. See `fairmind-gate` → "Authoring lessons the engine can't enforce". It has repeatedly caught green-but-wrong fixes a green gate passed.
- **Anything that lands after the green → record the tree that actually ships (`--record-transition post_ceremony`).** A green gate labels the tree it evaluated. If work lands between that green and the PR — a cleanup pass, review findings applied, a rebase — then the diff the human approves is **not** the diff the gate judged, and without a record that fact is unrecoverable afterwards. After the last such edit and **before** you present the final human gate, record it:
  ```bash
  python3 "${CLAUDE_PLUGIN_ROOT}"/scripts/run_gate_checks.py --record-transition post_ceremony
  ```
  It writes the ceremony instant, `HEAD`, the gate's own mutation signature and a line-count diff stat, and **nothing else** — and when the signature cannot be resolved it is stored as **null with its cause beside it**, never as an empty list: "nothing was touched" and "we could not tell" are different facts, and a consumer that cannot tell them apart guesses wrong. Beyond that it writes nothing — `status`, `confirmations` and `iterations[]` are byte-untouched, so recording is not an evaluation: it cannot move the budget, the failure counters or the confirmation streak. It **refuses on any loop that is not `passed_pending_human`** (a ceremony before the gate is green has no meaning), and it fails **closed** on a recorded `worktree.path` that no longer resolves to a real registered worktree — rather than recording the main tree's signature as if it were the worktree's. Add `--dry-run` to see exactly what it would record without writing anything. **Last write wins**, so re-run it after every further round of post-green edits — the tree that ships is the last one. Downstream this becomes a divergence *magnitude* — two one-way digests, a boolean and a count of changed paths, **never a path list and never diff content** — and a divergent loop is **flagged, never dropped**. There is deliberately **no `merge` transition to record**: the client emits the join key, and the merge itself is derived downstream from code ingestion and git history, so nothing here claims a merge sha.
- **The human's verdict → record it (`--human-gate <verdict>`), before re-arming and before the flush.** The final gate is a human decision, and it is the one label the whole loop exists to produce — so it goes onto the loop rather than staying in the conversation:
  ```bash
  python3 "${CLAUDE_PLUGIN_ROOT}"/scripts/run_gate_checks.py --human-gate approved
  python3 "${CLAUDE_PLUGIN_ROOT}"/scripts/run_gate_checks.py --human-gate approved_with_changes_applied_first
  python3 "${CLAUDE_PLUGIN_ROOT}"/scripts/run_gate_checks.py --human-gate rejected_and_re_armed --rearm-cause <cause>
  ```
  Three verdicts, and no others: **`approved`** (the human approved the tree the gate labelled), **`approved_with_changes_applied_first`** (approved after post-green edits — pair it with the `post_ceremony` record above, which says what those edits were worth), **`rejected_and_re_armed`**. A rejection **requires** `--rearm-cause`, one of **`review_finding_substantive`**, **`gate_evidence_insufficient`**, **`false_green`**, **`contract_defect`**, **`scope_violation`**, **`requirements_changed`**, **`other`**; the two approve verdicts **refuse** it. A value outside either enum exits non-zero **before** touching disk, and `--dry-run` previews the row without appending it.
  The verb **appends** — one row per gate visit, never overwritten, and a re-arm never clears the list. It does **not** re-arm: the human still runs `--arm` afterwards, and the verdict must be recorded **first**, because `--human-gate` refuses on a loop that is not `passed_pending_human` and `--arm` flips it straight to `running`. Correct a mis-typed verdict by simply re-running the verb — the last row recorded for a round is the operative one, and an append-only record is the one shape a verdict cannot be quietly erased from. Each row carries its round's iteration number and **no clock**: a human-authored record carries sequence position only. (That number is **null** on a loop that went green before the engine started recording the flip — left null rather than searched for backwards, since a guess wearing a number is worse than an absence.) (⚠️ Stated rather than left silent, because the residual is real. The asymmetry this note used to describe — the `arm` audit entry shipping its own timestamp while these rows did not — was **closed on 2026-08-20 (JC11)**: the `arm` entry and the `arm` transition row are both clockless now, which is what stops the **re-arm** instant leaving the machine. What still leaves is the **first** arm's instant, as `started_at` and inside `loop_id`, since a fresh `--arm` writes both from one clock read. And the rows on either side of an arm are agent-authored and keep their clocks, so the moment stays **bracketed**. ⚠️ Usually that bound is wider than the instant; **sometimes it IS the instant** — measured 2026-08-20 across 45 `arm` rows, widths 42 s to 43,119 s (median 1,228 s), with **1 of 22 re-arms** sharing its second with the adjacent agent row, which puts that instant on the wire verbatim. What these rows add is a verdict with no clock of its own, on the approval path that previously left no record at all.)
  ⚠️ **These verdicts are WEAK labels. Nothing downstream may treat them as ground truth.** One approver, normally the same person who drove the loop — **maker ≈ checker** — with no second annotator and therefore no inter-annotator agreement to compute. They exist to **pre-fill an annotation queue**, not to settle whether the work was good.
- **Budget exhausted → `blocked_*`.** Present the report and flag for the human. The loop never runs indefinitely. The report ends with a **cost-ask** — the remaining red checks, the trend, and the exact `--extend-budget` command.
- **Scope violation → `blocked_scope`.** Only when `contract.scope.allowed_paths` was declared (step 3): a mutated path outside it hard-stops the loop, naming the path and its attributing agent — this is not a budget or check failure, it never consumed either. Present it for the human to reconcile (revert/relocate the out-of-scope mutation, or amend the declared scope) before re-arming; do not treat it as a check to fix and iterate past.
- **Worktree degraded → `blocked_worktree`.** Only when `worktree.{path,branch}` was recorded (step 1's optional isolated worktree): if the path stops resolving to a real, registered worktree of this repo, the gate refuses to evaluate anything against the main tree instead and hard-stops here — again not a budget or check failure. Present it for the human to resolve — re-create the worktree (`loop_worktree.py --create --task-ref <ref>`) or clear `state["worktree"]` — before re-arming.
- **Dashboard:** render `python3 "${CLAUDE_PLUGIN_ROOT}"/scripts/loop_dashboard.py --md` and include the table in the closing report — this loop now shows as its finalized 🟢/🔴 row with its tool-call + token stats and the run totals (the engine appended the ledger row on the terminal transition).
- **Presenting the trace ledger:** when the report covers `.fairmind/trace/<taskRef>.jsonl`, summarize it as a digest — total ops, breakdown by `kind` (`mutate`/`exec`/`dispatch`/`read`), and the mutated files with the agent that touched each. Never paste raw JSONL into the report; give the file path, and show raw lines only if the user explicitly asks for them.
- **Agentic Insights terminal flush, on close.** Once the loop reaches a terminal status, flush what this close produced to project-context: run `python3 "${CLAUDE_PLUGIN_ROOT}"/scripts/insights_flush_payload.py --emit all --out`.

  ⚠️ **Run the two lifecycle verbs above BEFORE this flush** — `--record-transition post_ceremony`, then the human's `--human-gate` verdict. This is a convention with a data consequence, **not** something the engine enforces: nothing refuses a flush that precedes a verdict. The payload is built from `loop-state.json` at flush time, while the sync cursor keys a flushed close by `loop_id` **and the ledger row's `closed_at`** — stamped when the gate flips to `passed_pending_human`, and *not* re-stamped by a later `loop-state.json` write. So once a category has been `--commit`ted, that same close is never pending again (`pending_loop`, `scripts/insights_flush_payload.py`) and a ceremony or verdict recorded afterwards never reaches the wire. Verified 2026-08-14 by staging a `passed_pending_human` close, committing the loop category, then writing a verdict into `loop-state.json` and re-running `pending_loop` — still `None`. A rejection is the benign case: the loop is re-armed, closes again with a fresh `closed_at`, and that later close carries the whole append-only verdict history.

  The payload also carries a **consent stamp** (the classes and their defaults are in `INTERNALS.md` → *Consent classes*): the classes granted **when the data was collected**, alongside the classes actually **honoured** in this payload after the live resolution at flush. A withheld class empties its own fields *and the stamp says which* — so an empty field under a granted class reads as genuinely empty rather than as something withheld.

  `--emit all --out` writes the payloads to a file outside the repo and prints only a short summary — `{"out": "<path>", "bytes": <n>, "categories": {"loop": <n|null>, "decisions": <n|null>, "audit": <n|null>, "brain": <n|null>}}` — so **`Read` the `out` path** to get the payloads themselves. **Do not drop `--out`.** Without it the payloads go to stdout, a Bash tool result is capped at **30,000 bytes**, and a real close already exceeds that (measured 2026-07-26: `--emit all` is 28,995 B in the project-context service, and 39,688 B on this plugin's own `loop-t8` close — that one is reproducible only when `active-context.json` names T8, since the trace is resolved from `task_ref`, not from `--base`). Past the cap the harness hands you a ~2 KB preview **and says so**, naming a file it saved the rest to; the truncation announces itself, but proceeding from the preview does not — a fleet number reconstructed from a partial view, a skipped category, or a failed close all look like success from inside the turn. The MCP door itself has no body cap, so this is a channel problem, not a rejection.

**If the `out` file is itself too large to read in one go**, `Read` returns a prefix and says the file is too long. The payload is written INDENTED precisely so that case is recoverable: page it with `offset`/`limit`, or re-run per category — `--emit loop --out`, `--emit decisions --out`, `--emit audit --out` each write their own smaller file, and `--commit <category>` works exactly the same way afterwards. Never assemble an MCP call from a partial read. For each category whose value in `categories` is non-null, call the matching MCP tool — `mcp__Fairmind__Insights_record_loop_stats` for `loop`, `mcp__Fairmind__Insights_record_agent_decisions` for `decisions` — then run `python3 "${CLAUDE_PLUGIN_ROOT}"/scripts/insights_flush_payload.py --commit <category>` **only after that category's MCP call succeeds** — one `--commit <category>` per call that actually returned success. **`decisions` is a list of batches, and each batch is its own call** with that batch's own fields: this loop's decisions (every row recorded since its Phase 0 repoint) under its `session_ref`/`task_ref`, and — when the ledger still holds rows recorded before that repoint — a second batch whose `session_ref`/`task_ref` are `null`. When `active-context.json` carries no usable `decisions_start_line`, the null batch is the only one: every pending decision leaves unattributed, never under this loop's refs. Send a null batch as-is and never merge batches: the door stamps a batch's refs onto every row it stores, so a merged call relabels older decisions as this loop's. `--commit decisions` comes once, after **every** batch returned success. 🔴 **Never `--commit all` from this block.** The CLI still accepts `all` and it commits every category, including `brain` — which is sent two blocks later at the human gate and may be switched off for this repository entirely. A bulk commit here marks rows delivered that nothing sent, and a cursor that says delivered is never pending again. A failed or partial send must stay **uncommitted**: do not commit a category whose call errored or did not complete — it stays unflushed on disk and `/fairmind-sync-insights` retries it later, so `--commit` never marks unsent data as sent. If the Fairmind MCP is not connected at all, skip the calls the same way: the payloads stay on disk unflushed, and `/fairmind-sync-insights` picks them up later — a mode, not an error.
- **Studio task-lifecycle write-back, only after the human approves.** Once the human approves a `passed_pending_human` loop — never automatically on a green gate, mirroring the no-auto-merge rule above — reflect the result onto the Studio task itself, attempting the two calls independently so a failure in one never masks the other: `<task_id>` is the Studio task id that the loop's `task_ref` resolves to (the ref set by Phase 0's repoint into `active-context.json`/`loop-state.json`), and `<project_id>` is the project from that same `active-context.json`. `mcp__Fairmind__Studio_bulk_update_status(ids=[<task_id>], status="passed", entity_type="task")` advances the task's status, and `mcp__Fairmind__Studio_process_journal(task_id=<task_id>, journal_content=<journal contents>, project_id=<project_id>)` attaches the loop's journal to the task as activities — `journal_content` is the journal's file **contents**, not a path: read every `${FAIRMIND_BASE}/journals/<taskRef>_*.md` matching this task ref (concatenating them when more than one agent journaled) and pass the combined text as `journal_content`. Loop-outcome → Studio-status mapping: the human-approved `passed_pending_human` outcome pairs with the Studio `passed` status — Studio's task status is drawn from the `ImplementationState` vocabulary, and `passed` is the member meaning checks passed and the human signed off, awaiting the human's own separate merge action: the loop reaching green plus this approval is not the merge itself (the flip to `merged` is a later, human-driven step), so `passed` — never `completed`/`done`, neither of which is an `ImplementationState` member — is the accurate state at write-back time. If either `Studio_*` tool is absent (PC-12 not yet shipped server-side, or the Fairmind MCP not connected) — or a write is denied (the caller needs `editor+` on the project) — do not fail the close: report each write that failed as **not synced** in the Exit report, independently, since a status update can succeed while the journal attach fails or vice versa. This write-back has no on-disk queue and approval happens out-of-band, so it cannot be picked up the way the insights flush above is — the only recovery is a **rerun**: re-running the loop to its human-approved Exit re-attempts both MCP calls once PC-12/the MCP connection is available.

- **Brain write-back, only after the human approves.** Same trigger as the Studio
  write-back above and the same failure rule — attempt each call independently, and report
  a failure as **not synced** in the Exit report rather than failing the close. What goes
  up is what the run itself produced:

  1. **Architecture decisions.** Emit them with
     `python3 "${CLAUDE_PLUGIN_ROOT}"/scripts/insights_flush_payload.py --emit brain --out`
     and `Read` the `out` path. The category is `build_decisions_batches` filtered to the
     rows the agents typed `kind: "architecture"` — a list of `fm-insights.decision/2`
     batches, the same contract and the same split as `decisions` — so send each batch as its
     own `mcp__Fairmind__Brain_record_decision` call with that batch's own `repository`,
     `git_remote`, `session_ref` and `task_ref` (`null` refs included, never merged). Then
     `--commit brain`, **only after every one of those calls returned success**.
  2. **Issues the loop surfaced and did not fix.** One
     `mcp__Fairmind__Brain_record_issue` per finding, drawn from `loop-state.json`: an
     advisory or quarantined check still red at close, and a completeness review that
     recorded `gaps`. Each needs a `natural_key` **you** author and that a re-run would
     author identically — `<task_ref>:<check id>` for a check, `<task_ref>:gaps` for the
     review — since that key is what makes a second close update the issue instead of
     filing it twice. There is no on-disk queue for these: an issue not recorded here is
     recorded on a later close, or not at all.

  🔴 **Everything lands as `proposed`, and you never call `Brain_set_status`.** The brain
  records a proposal for a person to confirm or reject in the review queue; confirming is a
  human act and no verb of this command reaches it.

  **This route has a switch, and the producer enforces it — you do not have to.** The
  `brain` key of `.fairmind-insights.json` (`/fairmind-config brain on|off|unset`, effective
  state on its `brain write-back` line, centrally forced where the platform speaks). When it
  is off, `--emit brain` returns `null` and no commit advances, so the rows stay pending and
  the repository can turn it back on. **Say in the Exit report that it was off** — the
  category being empty is the one case a reader could mistake for "nothing to send".

  **Say what left, briefly.** The Exit report names each record: kind, title, and the
  target repository — one line each, never the payload. A person who approved a gate and
  then finds out later that decisions went to the company brain was not actually told.

  ⚠️ **What this switch does NOT stop.** The same architecture rows also leave through the
  insights lane as part of `decisions`, which has no switch at all. `brain off` narrows
  which doors they go through; it is not "these decisions stay on this machine".
- **Extending the budget is a human-only verb.** Never extend from gate feedback or on your own initiative. When a loop is `blocked_*` and the remaining work is worth more budget, **ask the user first** with `AskUserQuestion`, then run the extension with their literal answer recorded in the audit trail:
  ```bash
  python3 "${CLAUDE_PLUGIN_ROOT}"/scripts/run_gate_checks.py \
    --extend-budget iterations=<n>[,failures=<n>][,timeout_min=<n>] \
    --user-confirmed "<the user's exact answer>"
  ```
  The engine refuses `--extend-budget` on a `running` loop (only `blocked_*` is extendable) and appends an `extend_budget` audit entry to `iterations[]` recording `user_confirmed`. Resuming also **zeroes the confirmation streak and every check's `consecutive_failures`**, so the granted budget is not immediately re-consumed by a stale counter. The final human gate reviews that audit trail. There is no `--force` and no fake technical lock — the guard is procedural and auditable.
- **Recovering a loop wedged in `running` (human-only).** If the Claude Code session that armed a loop is gone (crashed/closed), the loop can pin itself in `running` with no engine path out: `--arm` refuses a running loop, `--extend-budget` refuses a non-blocked one, and a fresh session's Stop hook silently no-ops on the ownership mismatch. `--recover` is the one way out — but because a session-id mismatch is also exactly what a *second, concurrent* session would show while the first is still legitimately driving the loop, recovery is gated on an **explicit human confirmation, never on the mismatch itself**. Ask the user first, then:
  ```bash
  python3 "${CLAUDE_PLUGIN_ROOT}"/scripts/run_gate_checks.py --recover --user-confirmed "<why the owning session is gone>"
  ```
  It transitions `running` → `blocked_recovered` (a `blocked_*` status), clears `owner_session`, and appends a `recover` audit entry recording `user_confirmed`. Then `--arm` re-arms it (or `--extend-budget` grants budget) so a fresh session can resume. Refused on any non-`running` loop (already recoverable via `--arm`/`--extend-budget`) and without `--user-confirmed`. Honors `--dry-run`.

## Notes

- The loop is a no-op signal outside itself: without `loop-state.json` (or with a terminal status), the Stop hook does nothing and the interactive workflow is untouched.
- The main turn ends only when the **gate** (`loop-check.sh`, Stop) passes; separately, each code-mutating **sub-agent** must satisfy the **journal** hook (`check-journal.sh`, SubagentStop) before it can finish.
- **Human steering channel.** A human can drop a redirect / "don't repeat X" / a piece of context into `${FAIRMIND_BASE}/steering.md` by hand at any point in the run; the maker reads it first thing every iteration (see the "Maker turn" bullet above). It complements the gate-initiated signals — STRATEGY TURN (routed to the checker) and CONTRACT CONFLICT (routed to the Technical Lead) — as the human-initiated counterpart to those engine-initiated ones. Because it lives under `${FAIRMIND_BASE}` (hence under `.fairmind/`), it gets the same structural exemption as `loop-state.json`/journals/trace (`_is_loop_workspace_path`): editing it is never a code mutation, never trips `blocked_scope`, and never satisfies or breaks a check. It is user-authored only — no script ever emits it. See `fairmind-gate/references/steering.md` for the full contract.
